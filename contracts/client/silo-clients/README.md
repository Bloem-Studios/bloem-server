# Silo client compatibility check

Silo's own apps must work unchanged against a Bloem server. This check proves
it the direct way: it asks Bloem and upstream Silo the same questions, the way
Silo's apps ask them, and fails when the answers differ in anything an app
reads. Bloem may add to an answer; it may not drop, retype or refuse what
Silo gives.

Commands assume the repository root is the cwd and `upstream/main` is fetched.

```sh
make silo-client-compat                                       # build both, seed, compare
make silo-client-compat SILO_REF=<sha>                        # against another Silo commit
make silo-client-compat SILO_CLIENT_COMPAT_ARGS=--apps-only   # only what the apps call
python3 scripts/bloem/local-gate.py run --only compat         # the same, as a local-gate phase
python3 scripts/bloem/silo-client-compat/compat_test.py       # the comparison rules' tests
```

A run took 4 minutes on a busy develop machine with Go's build cache warm:
2.5 minutes to build the two servers one after the other (most of it Silo),
then about a minute and a half to start them, seed them and replay about 4,100
requests. With a cold build cache the builds take 2 to 3 minutes longer. It needs Docker, Go and
`ffmpeg`, and uses ports 18230 (Bloem), 18231 (Silo) and 18232 to 18235 (their
PostgreSQL and Redis); `SCC_PORT_BASE` moves the block. It removes its
containers and work directory when it ends, unless `--keep` is given.

## What it does

1. **Builds** Bloem from the tree and Silo at `SILO_REF`, by default the merge
   base of `HEAD` and `upstream/main`: the Silo commit Bloem last merged.
2. **Starts** each on its own fresh PostgreSQL and Redis.
3. **Seeds** both the same way, through Silo's public API only: initial setup,
   a movie library and a series library of tiny `ffmpeg` videos (one movie, two
   episodes), a scan of each, polled until the libraries report a finished scan
   and the catalog lists the titles, a second account, a profile without a PIN
   and one with. If Bloem cannot be set up this way, that is reported as a
   divergence. The seed also turns request rate limiting off, as an operator
   can, and restarts both servers, since its windows depend on timing.
4. **Replays** every operation in [calls.json](calls.json), plus every other
   `GET` in Silo's OpenAPI as a third-party client might call it, as seven
   people:

   | Persona | Who |
   |---|---|
   | `admin` | the server's administrator on its primary profile |
   | `user` | an ordinary account on its own profile |
   | `pin` | a PIN-locked profile after `verify-pin` |
   | `anon` | no sign-in |
   | `account` | signed in, no profile picked yet |
   | `locked` | the PIN-locked profile without its PIN proof |
   | `foreign` | an ordinary account naming the administrator's profile |

   Reads go first, then writes, then deletes, then sign-outs. Path ids come
   from what each server seeded; ids the seed has no value for are the same
   invented id on both servers, so their refusals are compared too. Request
   bodies are Silo's OpenAPI required members with sample values, corrected
   where needed in `scripts/bloem/silo-client-compat/requests.json`. Follow-ups
   replay what an answer names: the playback plan's stream URL (as a byte
   range, and with the stream token alone) and the events WebSocket with its
   ticket, up to the server's hello frame.
5. **Compares** each pair (`scripts/bloem/silo-client-compat/compare.py`):
   status, problem type, the headers apps read (ETag, Location, Retry-After,
   ranges, cache, the WebSocket subprotocol), and every JSON field's presence
   and type. Values are not compared, so ids, timestamps and tokens never
   differ; the rules for the rest are written down at the top of
   `compare.py`. A field null on one side and set on the other fails only when
   a Silo app requires it. The few values apps check before they accept a
   server, such as `api_major`, are compared exactly.
6. **Reports** each divergence by operation and persona and exits non-zero.

## The call list

`calls.json` is generated by `scripts/bloem/silo-client-compat/extract_calls.py`
from the shipped sources of the Silo apps (tests, docs and developer spikes
skipped). For each operation it records the methods, query parameters, headers
and body fields the apps send, and the response fields they decode, with the
apps that fail without a field listed under `required_by`. It reads source text
with patterns, not a compiler, so it is close rather than exact: each entry
names its source lines, `overrides.json` beside the script adds what the
patterns miss, and `unmatched` lists the paths it could not place. The check
compares whole answers either way, so a field the list misses still counts.

Routes are matched against Silo's OpenAPI and route inventory at
`silo_routes_from`. To refresh the list, clone the three apps fresh into one
directory and run `make silo-client-calls SILO_APPS=<that directory>`.

## The allowlist

`scripts/bloem/silo-client-compat/allowlist.json` lists the differences Bloem
has today, each with its reason. It may only shrink: a run fails when an entry
was added since `origin/main`, when an entry has no reason, and when an entry no
longer matches anything, so a fixed difference has to leave the list.
`compat.py check-allowlist` checks the file alone.
