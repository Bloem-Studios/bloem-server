# Native Pastime managed tracking

Bloem's `internal/managedtracking` service enrolls one source account as one Pastime account with independently tracked household profiles. It registers `bloem.managedtracking.v1.ManagedTrackingHost` through the optional installation-bound broker hook. Only the installed `bloem.pastime` plugin receives the service; every RPC checks the current installation grant and tenant authority. This is a separate protocol namespace, not a public SDK upgrade. The server remains on SDK v0.24.0 and the plugin on v0.26.0; each executable links one SDK version.

## Durable authority

The migrations add a stable instance identifier, tenant-scoped grants, credential generations, profile projections, lifecycle records, snapshots, enrollment receipts and playback authority. Profile projection filters by organization. Default identifiers survive tombstones; active defaults precede children in immutable inventory. Identity writes advance committed revisions under one publication clock row, which only identity triggers and new inventory snapshots lock. Inventory pages contain at most 100 rows, expire after ten minutes, and use opaque issued cursors; at most sixteen snapshots coexist per installation. Only complete issued snapshots authorize lifecycle acknowledgement.

The inventory carries no email address, and account and profile names are trimmed, stripped of control characters and cut to 80 characters (with a fallback for an empty name), so every row is acceptable to Pastime and one odd name cannot stall a tenant's reconcile.

`EnsureConnection` checks exact source revisions, activity, destination IDs, generation and a stable JSON-tuple enrollment hash. It atomically commits encrypted profile-bound watch-sync credentials and replay receipts. An identical retry converges only when the stored connection still holds exactly that enrollment; a removed, disabled or overwritten connection is rewritten. Changed content with the same enrollment ID conflicts. Disabled accounts/profiles clear tracking credentials without deleting retained history.

Managed credentials have one writer. A `BEFORE UPDATE` guard on `watch_provider_connections` keeps the provider account, tokens and plugin credentials of a granted installation's rows unless the transaction set `bloem.managed_tracking_writer`; generic watch-sync upserts built from an older in-memory connection still update errors and sync times but cannot restore a revoked credential.

Every grant has a `generation` and a `min_generation`. `GetInfo`, the reconciler's entry point, raises `generation` thirty days after the last renewal, ahead of the destination credential's ninety-day expiry; existing connections stay enabled and earlier enrollments keep authorizing events until each profile is re-enrolled. Explicit rotation, revocation and reactivation raise both, which cuts every older credential at once and disables connections. `Describe`, used by the operator command, has no side effects. Revoked grants reject future requests.

## Verified sign-in identity

Each inventory profile carries its account's verified sign-in identity in `verified_identity_issuer` and `verified_identity_subject` (proto fields 11 and 12), or neither. Pastime uses the pair to attach a person's own login to the managed account that holds their tracked history. Email never links accounts.

The host derives the identity from the account's `plugin_auth_identities` rows in enabled `silo.auth.oidc` installations; `bloem_managed_verified_identity` implements the rule:

- `silo.auth.oidc` builds `external_subject` as `iss|sub` from the verified ID token, and Bloem login matches on it. The host splits it at the first `|`. It never reads the installation's configured issuer, because that config is one encrypted envelope that also holds the client secret.
- A row is valid when the issuer is an `https://` URL of at most 500 characters without credentials, query, fragment, whitespace or control characters; the subject is non-empty, at most 255 characters and free of control characters; and the `issuer` column is empty or equal to the parsed issuer. An empty `issuer` column (rows linked before the column existed) takes the parsed issuer.
- Any invalid row (an Entra `tid|oid` key, for example), rows naming more than one distinct pair, or a key that another account also holds in an enabled `silo.auth.oidc` installation leaves the account without an identity. The shared-key rule applies to both accounts.
- Links an administrator made count like sign-in links: both already authorize Bloem login for that account.

The pair lives in `bloem_managed_profiles.identity_issuer`/`identity_subject`, identical on every row of an account. `bloem_managed_refresh_account` writes it, including on tombstones. Row triggers on `plugin_auth_identities` (insert, delete, and updates that change the key, account, issuer column or installation) and on `plugin_installations` (enabling, disabling or changing the plugin of a `silo.auth.oidc` installation) call `bloem_managed_refresh_identity` for the accounts on both sides of the change and for every account holding the same key. It republishes an account only when its derived identity differs from the projection. Sign-ins and provider re-checks rewrite the `issuer` column of existing rows; those compare equal and take no clock lock and no revision. Removing an installation cascades to its rows, which the row trigger covers.

Identity triggers serialize on one transaction-scoped advisory lock (`bloem.managed_identity`) before reading links, so concurrent link changes see each other's commits and the shared-key rule holds under concurrency. `bloem_managed_refresh_account` takes the same lock before the clock row, so every publisher takes the identity lock, then the clock, then projection rows; snapshots take only the grant and the clock. Identity writers still never wait on grants.

`EnsureConnection` compares the whole profile, identity included, with the projection, so a plugin cannot drop, alter or inject an identity. The broker also refuses a half-set pair or one outside the shape limits. The `Profile` JSON fields are `omitempty`: an account without an identity serializes exactly as before, so enrollment payload digests recorded earlier still replay. `EnrollmentID` does not hash the identity; a changed identity is a new account revision, which already yields a new enrollment ID.

The migration that introduced the identity (`20261011184920`) deletes in-flight snapshots and republishes only accounts that gain an identity. Its Down republishes every account that had one, with the identity cleared, so roll it back before running an older server binary. Apply it with the release binary: a previous binary that keeps reconciling after the migration would deliver the new revisions without the identity.

## Playback provenance

Only Pastime outbound clients are wrapped. Before calling the plugin, the host vouches for each event separately and records a receipt: the digest of the deterministic serialization of the forwarded SDK event, the authenticated source binding and a source revision. `ResolveEvent` validates those receipts and current enrollment authority. Arrival time and caller timestamps never establish ordering.

- Source revisions come from the `bloem_managed_playback_revision` sequence, not a shared row, so watch-history and scrobble writes never wait on each other. History sources are recorded only for profiles of a tenant with a grant; the grant backfills its tenant's completed history, and a history row committed concurrently with that backfill gets its source when first exported. Scrobble sources are recorded only for connections whose provider key is exactly a granted installation's `plugin:<id>:pastime`.
- A history event takes the oldest source of its viewing on the row's current media item, so a viewing moved to another item exports for that item. A live event takes the latest time its session reached exactly that action and position; duration and the session's stored completion flag are not compared, because watch sync does not store them on every update.
- A completion is anchored to the profile's current history row: its media item decides the entity and its watch time becomes the occurrence, so the live stop, the history export and any retry of one viewing carry one consumption payload. A stop whose session recorded a completed viewing is delivered as that completion even when the session row lost the flag (the startup sweep's re-sent stop).
- The plugin receives each event under a host-derived ID, a digest of its payload. Watch sync reuses an event ID for different payloads (a resumed session restarts with the same START ID; the sweep re-sends a STOP with a new time); payload-derived IDs keep each distinct while exact retries stay idempotent. Results return under the caller's IDs.
- An event the host cannot vouch for (invalid, no source, a history row that is gone or not completed, a duration below one second) is answered `REJECTED` without reaching the plugin, and the rest of its batch proceeds. Only the batch's own authority (grant, enrollment, credential) or storage fails the whole call.

Completed history and live delivery for one viewing share a stable consumption ID, preventing duplicate plays while preserving independent profiles and genuine rewatches. Receipts older than thirty days are pruned by `GetInfo`; a plugin resolves a receipt only within the `ApplyEvents` call that recorded it.

The plugin exports movie/episode start, pause and stop plus completed `MARK_WATCHED` history. Ordinary playback completion requires the host's explicit completion flag; no percentage inference is added. Reverse sync, unwatched changes, ratings, favorites and lists remain disabled.

Pastime resolves trusted external catalog identifiers before transactional effects. It rejects title-only or destination-ID shortcuts. Separate provisioning and profile tracking credentials cannot authorize browser administration or household impersonation.

## Operations and verification

Commands assume the repository root is the cwd. Build `go build ./cmd/bloem-managed-tracking`; supply existing protected `DATABASE_URL` and `SECRET_KEY` through the operator environment. The backend-only command accepts `-action grant|info|rotate|revoke -installation N`; granting also accepts `-tenant UUID`. It prints only instance, scope and generation metadata, and `info` changes nothing. A grant backfills the tenant's history sources in one statement, so the command allows fifteen minutes. It is not a browser setup API.

Mirrored Silo switching: `internal/tenancy/bloem_managed_tracking_switching_test.go` and `internal/tenancy/bloem_managed_identity_switching_test.go` drive Silo-shaped writes to every table these triggers watch while the database is mirrored.

`TestRealPluginAndPastimeHouseholdAcceptance` uses separately compiled real plugin and real Pastime HTTP fixture processes, isolated PostgreSQL schemas and synthetic metadata. It covers three independent profiles, later additions/rename/deletion, completion/history overlap, stale history, the native watch-sync path (start, pause, resume and a completed non-confirmed stop), cancellation/reactivation, plugin restart and grant revocation. Explicit fixture binary paths and test database URLs are required; absent fixtures skip this test. Fresh migrations and the pinned Silo mirrored-database switching check passed. The switching image was a local acceptance image, not a production release artifact.

See Pastime's `docs/managed-tracking-rollout.md` for coordinated release and rollback. Automatic enrollment remains inactive until an explicitly approved household pilot. This host sends the verified sign-in identity described above; claiming a managed account at login is Pastime's side of the contract. Email never merges accounts. User-managed exclusion remains separate product work. Until exclusion exists, a user who deletes or disables a managed connection sees it restored at the next reconcile, because the profile stays enrolled.
